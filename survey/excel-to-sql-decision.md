# 시장품질 엑셀 정형화: MariaDB로 바로 넣을 것인가

- 배경: 시장품질 문서 중 xlsx 비중이 높고, 단일 파일이 최대 ~100MB
- 질문: MariaDB 같은 정형 SQL로 DB화하는 것이 좋은가
- 관련 문서: `market-quality-rag-improvement.md`, `xlsx-20-samples-layer1.md`, `format-pipelines/04-xlsx.md`
- 재검토: 2026-09-05

## 결론

**정형 DB로 빼는 것은 맞고, 원본 엑셀을 MariaDB 테이블로 1:1 적재하는 것은 비추천이다.** 숫자는 SQL, 설명은 RAG로 나누되, 100MB급 품질 엑셀은 **원본 보존 레이어**와 **분석용 스키마**를 분리해야 한다.

| 선택 | 판단 |
|---|---|
| 엑셀을 Milvus에 넣는 것 | 하지 말 것 |
| 엑셀을 SQL로 조회 가능하게 만드는 것 | 해야 함 |
| 파일마다 MariaDB 테이블을 만드는 것 | 하지 말 것 |
| 클레임/불량 같은 공통 사실을 정규화해서 MariaDB에 넣는 것 | 목표가 맞음 |
| 바로 MariaDB만 구축 | 너무 이름. 먼저 Parquet 랜딩이 안전함 |

MariaDB가 나쁜 도구여서가 아니다. **엑셀 양식이 제각각인 상태에서 RDB에 바로 넣는 비용**이 문제다.

## 왜 바로 MariaDB면 실패하기 쉬운가

시장품질 엑셀은 대개 DB 테이블이 아니라 **사람이 보는 보고서**다.

- 시트마다 헤더 행 위치가 다름, 병합 셀, 제목/단위/주석이 데이터 위에 있음
- 한 시트에 표가 여러 개
- 컬럼명이 월보마다 미묘하게 다름 (`클레임건수` / `Claim Qty` / `건수(대)`)
- 100MB xlsx는 압축된 XML이라, 풀면 수백만 행·메모리 폭주가 흔함
- 파일 하나가 “적재용 원장”인지 “그달 스냅샷 보고서”인지가 섞여 있음

이 상태에서 MariaDB에 넣으면 보통 아래 둘 중 하나가 된다.

1. **파일/시트당 테이블** → 테이블이 수백~수천 개. Codex가 어떤 테이블을 칠지 모름.
2. **억지로 한 스키마** → 매핑이 깨진 채 적재. 숫자는 들어가 있는데 의미가 틀림.

담당자가 원하는 질문(`최근 3개월 이 차종 클레임 건수`)은 2번이 맞아야 답이 나온다. 그 작업의 본질은 DB 설치가 아니라 **양식 → 표준 스키마 매핑**이다.

## 권하는 구조: 2층

```
xlsx (최대 ~100MB)
  → calamine/polars 스트리밍 (openpyxl 전체 로드 금지)
  → 1층: Parquet 랜딩 (파일/시트 원본, 스키마 그대로)
  → 2층: 표준 팩트 테이블 (MariaDB 또는 Postgres)
        claims, products, failure_modes, monthly_stats, ...
  → MCP
        list_tables / describe_table / query_tables
  → 벡터에는 테이블·컬럼 설명만
        “이 숫자는 claims 테이블에 있다”
```

**1층**은 깨지지 않게 원본을 남기는 곳이다. 100MB 엑셀을 페이지/시트 단위로 Parquet에 두면 재처리가 쉽고, DuckDB로 탐색도 된다.

**2층**이 담당자 인사이트용이다. 여기만 깨끗한 SQL이어야 한다.

MariaDB는 2층에 두는 것이 맞다. 1층까지 MariaDB에 넣으면 `VARCHAR` 덩어리·JSON 덤프가 되어 분석이 느리고 스키마가 지저분해진다.

## MariaDB를 쓸 때 / 쓰지 않을 때

회사 안에 이미 MariaDB가 있고, 담당자 여러 명이 MCP로 동시에 조회하며, 권한·백업·다른 시스템 조인이 필요하면 **2층은 MariaDB가 적절**하다.

아래면 MariaDB를 먼저 고집할 필요는 없다.

- 아직 표준 스키마가 없음
- 엑셀 양식이 너무 제각각이라 매핑 규칙이 없음
- 질문이 탐색적 집계 위주임 (월별, 차종별, 불량모드별)

이때는 DuckDB + Parquet로 2~4주 검증하고, 질문이 반복되는 팩트만 MariaDB로 올리는 편이 빠르다. DuckDB는 서버 운영 부담이 적고, 100MB급 분석에 잘 맞는다. 다만 멀티유저 서비스·권한 관리에는 MariaDB/Postgres가 더 낫다.

정리:

- **실험/매핑 검증:** DuckDB + Parquet
- **서비스화:** MariaDB(또는 Postgres) curated tables
- **둘 다:** 랜딩은 파일, 서빙은 RDB

## 100MB 엑셀에서 꼭 지킬 것

- 워크북 전체를 메모리에 올리지 말 것. **fastexcel/calamine**이 2026 Polars `read_excel` 기본 엔진이다. `.xls`/`.xlsb`/`.xlsm`/`.ods`도 같은 엔진으로 값을 읽는다. openpyxl은 차트·정의된 이름·병합 수리 폴백.
- xlsx를 MariaDB BLOB로 넣지 말 것.
- 피벗·차트·매크로 시트는 데이터 시트가 아님. 건너뛰고 메타만 남김.
- 날짜는 엑셀 시리얼 숫자로 들어오니 변환을 명시.
- 동일 월보가 매월 파일로 쌓이면 **스냅샷**으로 취급. 그냥 UNION 하면 중복 집계가 난다. `source_file`, `report_period`, `ingested_at`을 반드시 넣는다.

## MCP 쪽

Codex에 `SELECT * FROM 아무거나`를 주면 위험하고, 테이블이 많으면 모델이 헤맨다.

도구는 이렇게 쪼개는 것이 좋다.

- `list_tables(product, period)` — 어떤 표가 있는지
- `describe_table(name)` — 컬럼 의미, 단위, Grain(한 행이 무엇인지)
- `query_tables(sql)` — 읽기 전용, 허용 스키마만, LIMIT 강제
- 가능하면 SQL 대신 `filters` + `group_by` 같은 구조화 조회를 먼저 제공

벡터 DB에는 행 데이터가 아니라 **카탈로그**만 넣는다. 예: “`claims` 테이블, 한 행 = 클레임 1건, 컬럼: 품번, 차종, 발생일, 고장모드, 건수”.

엑셀 안의 긴 서술 칸(원인, 대책, 담당 의견)은 SQL 집계 대상이 아니다. 그 컬럼만 텍스트로 빼서 RAG 하는 하이브리드가 맞다.

## 실무 순서

1. 엑셀 20~30개를 열어 **반복되는 양식 3~5종**만 분류 (원장형 / 월보형 / 집계형).
2. 담당자 질문 20개를 SQL로 답이 나오는지 적어 보기.
3. 그 질문에 필요한 **최소 팩트 테이블 2~3개**만 설계. 예: `claim_event`, `monthly_quality_kpi`.
4. 100MB 파일 1개로 추출 → Parquet → 집계 쿼리 검증.
5. 그때 MariaDB 적재. 처음부터 3,100개를 RDB에 밀어 넣지 말 것.

엑셀이 많고 큰 상황에서는 “MariaDB로 DB화” 자체는 방향이 맞다. 다만 성공 조건은 DB 종류가 아니라, **파일 단위 적재가 아니라 시장품질 사실(클레임, 월별 KPI, 고장모드) 단위로 정규화하는 것**이다.

## 후속 확인

엑셀이 더 가까운 쪽에 따라 스키마가 달라진다.

1. 행 단위 원장 (클레임 한 줄이 한 건)
2. 월보/집계 보고서 (위쪽에 제목, 아래에 요약 표)
3. 둘 다 섞여 있음

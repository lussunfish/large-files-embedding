# 유사 xlsx 20개로 1층을 만드는 방법

- 배경: 비슷한 형태의 xlsx 20개를 LLM에 주면 1층(랜딩)을 어느 정도 정리할 수 있는가
- 관련: Claude가 대용량 파일 묶음에서 유의미한 데이터를 찾을 때 청크 임베딩 대신 다른 방식을 권함
- 관련 문서: `market-quality-rag-improvement.md`, `excel-to-sql-decision.md`, `format-pipelines/04-xlsx.md`
- 재검토: 2026-09-05

## 결론

20개면 1층 설계는 충분히 된다. 다만 엑셀 원본을 모델 컨텍스트에 넣는 방식이 아니라, **파일은 코드가 읽고 LLM에는 얇은 프로필만 주는 방식**이어야 한다. Claude가 청크 임베딩 대신 말한 것도 거의 이 계열이다.

유사 xlsx 20개는 **1층 추출기를 만들기엔 충분한 표본**이다. 3,100개를 이해시키는 입력이 아니다.

## Claude가 말했을 법한 용어

정확히 어떤 단어를 썼는지는 모르지만, “대용량 파일 묶음에서 유의미한 데이터를 찾아 정리할 때 청크 임베딩보다 나은 방법”으로 Claude가 흔히 권하는 것은 아래다.

| 용어 | 의미 | 지금 과제와의 거리 |
|---|---|---|
| **Text-to-SQL / NL2SQL** | 질문 → SQL → 표에서 계산 | 2층·질의용. 1층 정리의 이름은 아님 |
| **TAG (Table-Augmented Generation)** | RAG의 표 버전. 검색이 아니라 테이블 쿼리로 근거를 가져옴 | 청크 RAG 대체로 가장 가까운 학술 이름 |
| **Code interpreter / 코드 실행 분석** | 엑셀을 프롬프트에 넣지 않고 Python/DuckDB가 읽고, 모델은 결과만 봄 | Claude가 실무에서 제일 자주 권하는 방식 |
| **Schema alignment / 스키마 정렬** | 비슷한 파일 20개의 컬럼을 하나의 표준 스키마로 맞춤 | **1층 정리의 본업** |
| **Medallion (Bronze–Silver–Gold)** | 원본 적재 → 정제 → 분석 테이블 | 1층/2층과 같음 |
| **Metadata-first** | 행 전체가 아니라 시트/컬럼 설명·샘플만 모델에 줌 | 100MB에서 필수 |

청크 임베딩을 반대하는 이유: 엑셀의 진실은 “비슷한 문장”이 아니라 **행·열·집계**다. 모델이 셀을 읽는 게 아니라, **코드가 스캔하고 모델은 스키마를 설계**하는 쪽이 맞다.

실무에서 제일 쓸모 있는 이름은 **스키마 정렬 + 코드 실행 프로필**이고, 질의 단계 이름은 **TAG / Text-to-SQL**이다. Claude가 “임베딩 말고 다른 거”라고 했다면 이 둘 중 하나일 가능성이 크다.

## 20개를 주면 어디까지 되나

유사 양식 20개는 **데이터 전부가 아니라 양식의 표본**이다. 이걸로 1층의 규칙이 나온다. 3,100개를 모델이 읽는 구조가 아니다.

잘 되는 것:

- 시트 구성이 같은 가족인지 분류 (원장형 / 월보형 / 집계형, 보통 1~3개 패밀리)
- 헤더 행 위치, 병합 셀, 데이터 시작 행
- 컬럼명 동의어 사전 (`클레임건수` = `Claim Qty` = `건수(대)`)
- 표준 컬럼 초안과 파일별 매핑 표
- 날짜·숫자·코드 변환 규칙
- Parquet 랜딩용 추출 스크립트
- 20개에 대한 실패 리포트 (이 파일만 헤더가 3행, 이 시트는 표가 두 개)

잘 안 되는 것:

- 100MB 원본을 채팅창에 올리고 “의미 있는 데이터 찾아줘”
- 담당자만 아는 컬럼 의미 (`구분2`, `코드A`)의 확정
- 시트 안에 표가 여러 개인 보고서의 100% 자동 분할
- 피벗/차트/설명 칸을 데이터처럼 적재

체감 성공률은 “얼마나 비슷한가”에 달한다.

- **같은 템플릿의 월보 20개:** 1층 자동화 70~90%. 매핑 한 번 고정하면 이후 파일은 스크립트가 처리
- **같은 업무인데 양식이 3~5종:** 패밀리별로 매퍼가 필요. 20개로 패밀리 분류까지는 잘 됨
- **겉만 엑셀이고 레이아웃이 제각각:** 20개로는 분류만 되고, 공통 스키마는 억지가 됨

## LLM에 파일을 주는 방법이 핵심

채팅 업로드는 여기서 거의 실패한다. Anthropic 공식 한도(2026-09)는 **파일당 30MB, 채팅당 20개**다. 100MB 엑셀은 이 한도를 넘는다. 일부 Files API 경로는 더 크지만, 그래도 컨텍스트에 셀을 넣는 방식이 아니다. 웹 LLM에 xlsx를 통째로 주는 방식은 기각이다.

맞는 역할 분담:

```
20개 xlsx
  → (코드) 프로파일러가 파일마다 2~10KB JSON만 뽑음
        시트명, 행/열 수, 헤더 후보, 컬럼, 타입, null 비율,
        고유값 상위 N, 샘플 5행, 병합셀 여부
  → (LLM) 패밀리 분류 + 표준 스키마 + 매핑 YAML
  → (코드) 20개 전부 Parquet 랜딩
  → (LLM) 실패 파일만 다시 봄
  → 담당자가 컬럼 의미 5~10개만 확인
```

모델이 보는 것은 수백만 행이 아니라 **양식의 지문**이다. CLI 에이전트(Grok, Claude Code, Codex)가 웹 채팅보다 이 작업에 유리한 이유다. 파일을 읽지 않고, 파일을 읽는 코드를 쓰기 때문이다.

20개를 주면 실제로 하는 일:

1. calamine/polars로 시트 목록·크기·헤더 추정 (워크북 전체 메모리 로드 금지)
2. 20개 스키마 비교표
3. 패밀리 1~N개와 표준 컬럼 초안
4. `mapping.yml` + `xlsx_to_parquet.py`
5. 20개 변환 후, 깨진 파일만 목록화

이게 1층이다. MariaDB는 그 다음이다.

## 1층에 무엇을 남기면 좋은가

20개로 “의미 있는 데이터만 남기라”고 하면 모델이 임의로 컬럼을 버리기 쉽다. 1층은 반대로 **거의 버리지 않는 층**이어야 한다.

파일/시트당 Parquet 하나, 대략 이런 메타를 붙인다.

- `source_file`, `sheet_name`, `report_period`, `template_family`
- 원본 컬럼은 가능한 한 유지 (정규화는 2층)
- 헤더가 두 행이면 `col_클레임_건수`처럼 이어 붙이기
- 완전히 빈 시트, 차트시트, 매크로 시트만 제외
- 서술형 긴 칸(원인/대책)은 삭제하지 말고 그대로 둠. 나중에 RAG로 감

20개 표본의 목적은 데이터 축소가 아니라 **“이 양식은 이렇게 읽으면 된다”는 추출기**를 고정하는 것이다.

## 다른 LLM vs CLI 에이전트

| 방법 | 100MB × 20개 |
|---|---|
| 웹 Claude/ChatGPT에 업로드 | 용량 한도에 걸림. 일부만 보고 착각하기 쉬움 |
| 모델에게 셀을 읽혀 정리 | 느리고 숫자가 틀림 |
| CLI + 프로파일러 + 매핑 생성 | 이 문제에 맞는 방법 |

모델 성능 차이보다 **원본을 컨텍스트에 넣지 않는 프로토콜**이 결과를 가른다.

## 다음 단계

샘플 20개를 이 폴더에 주면, 업로드가 아니라 아래 순서로 진행한다.

1. 프로파일
2. 패밀리 분류
3. `mapping.yml`
4. Parquet 추출 스크립트

파일이 사내망에만 있으면 시트 스크린샷이나 헤더 행만이라도 같은 작업의 절반은 할 수 있다.

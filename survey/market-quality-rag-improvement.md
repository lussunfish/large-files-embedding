# 시장품질 문서 RAG/MCP 정확도 개선안

- 대상: 약 3,100개 제품 시장품질 문서 (PDF, DOCX, XLSX, DOC, MD 등, 최대 100MB)
- 현재 파이프라인: 파일 업로드 → Docling 변환 → Milvus 벡터 저장 → RAG MCP → Codex CLI 연동
- 목적: 시장품질 담당자에게 신뢰할 수 있는 인사이트 제공
- 포맷별 상세: `format-pipelines/` (2026-09 재검토)
- 이 문서 재검토: 2026-09-05

## 문제 정의

정확도가 안 나오는 핵심 이유는, 3,100개·최대 100MB·확장자 혼재 문서를 **하나의 Docling → 청크 → Milvus RAG**로 밀어 넣는 구조 자체에 있다. 시장품질 문서는 “비슷한 글”이 아니라 **서술 보고서 + 엑셀 수치 + 차트/표 + 품번·차종 코드**가 섞여 있어서, 텍스트 임베딩만으로는 담당자가 원하는 답을 자주 놓친다.

## 왜 지금 방식에서 정확도가 막히는가

시장품질 담당자가 실제로 묻는 질문은 대략 네 종류다.

| 질문 유형 | 예 | 지금 파이프라인이 약한 이유 |
|---|---|---|
| 코드/키워드 조회 | 품번, 클레임번호, 차종 | 의미 검색은 약하고, 키워드/정확 매칭이 강해야 함 |
| 수치/집계 | 최근 3개월 클레임 건수, 불량률 | 엑셀을 문장으로 잘라 넣으면 행·열 관계가 깨짐 |
| 차트/표 해석 | Pareto, 월별 트렌드 그래프 | 기본 변환만으로는 그림 속 숫자가 안 남음. 차트 숫자 추출 또는 비전 검색이 필요 |
| 원인·대책 서술 | 8D, 근본원인, 재발방지 | 섹션 문맥이 잘리면 대책이 다른 이슈와 섞임 |

실패는 보통 모델이 멍청해서가 아니라, **검색에 넣을 증거가 이미 깨져 있거나, 아예 인덱스에 없는** 경우가 많다.

구체적으로는 아래 손실이 겹친다.

1. **파싱 손실**  
   Docling은 PDF/DOCX 레이아웃에는 강하지만, 100MB급·스캔본·복잡한 표·엑셀 시트에서는 정보가 잘리거나 평탄화된다. `.doc`는 LibreOffice 변환이 필요하고, 숨기면 hang/프로필 충돌(#3819)을 못 본다. 차트는 기본 파이프라인에선 그림으로만 남고, `--enrich-chart-extraction`(bar/pie/line → 표)을 켜야 숫자가 나온다.

2. **청킹 손실**  
   마크다운으로 보낸 뒤 고정 길이로 자르면 표가 반으로 갈라지고, 제목과 본문이 떨어지고, 100MB 문서 하나가 수천 청크가 된다. 검색 노이즈가 폭증한다.

3. **검색 손실**  
   의미 벡터만 쓰면 `ABC-1234` 같은 품번은 거의 못 찾는다. 메타데이터(제품, 기간, 문서유형, 지역) 필터가 없으면 3,100건 전체가 매번 경쟁한다.

4. **생성 손실**  
   MCP가 `search(query)` 하나면 Codex는 top-k 문장만 보고 답을 만든다. 담당자가 필요한 건 “관련 문장”이 아니라 **해당 섹션, 해당 시트, 해당 페이지**다.

연구/실무에서도 같은 패턴이 반복된다. 텍스트 RAG의 병목은 임베딩 모델보다 **ingestion(파싱·청킹)** 인 경우가 많고, 표 질문에서는 Docling HybridChunker(`repeat_table_header`, `contextualize`)만으로도 정확도가 크게 오른다. 차트·스캔·레이아웃이 중요한 문서는 페이지 비전 검색(2026 기준 **ColQwen2/2.5가 ColPali보다 ViDoRe·다국어에서 앞섬**)이 텍스트 OCR RAG를 이긴다. 숫자 집계 질문은 TAG/Text-to-SQL이 RAG보다 맞다.

## 목표 구조: “하나의 RAG”가 아니라 “질문 유형별 도구”

Codex CLI에 MCP를 붙인 선택은 좋다. 에이전트에게는 벡터 검색 하나가 아니라 **역할이 다른 도구**를 주는 편이 맞다.

```
문서 입고
  ├─ PDF/DOCX/MD  → Docling JSON → HybridChunker + (선택) 페이지 비전 인덱스
  ├─ XLSX/XLS     → calamine/polars → Parquet 1층 → SQL 2층 (벡터에 넣지 않음)
  └─ 이미지/차트  → Docling chart extraction(막대/원/선) 또는 VLM. 스캔은 RapidOCR korean

공통 메타데이터: 제품, 차종, 품번, 기간, 문서유형, 지역, 파일경로, 페이지/시트

MCP tools (Codex가 조합)
  - list_documents(filters)
  - search_passages(query, filters)      # 하이브리드 + rerank
  - get_outline / get_section            # 문서를 트리로 읽기
  - query_tables(...)                    # 엑셀/추출 표
  - get_page_image(doc, page)            # 차트/스캔 확인
```

핵심: **엑셀은 RAG로 풀지 말고, 서술 문서는 RAG로, 차트는 비전으로** 나눈다.

## 개선 순서 (ROI 높은 것부터)

전체를 한 번에 바꾸지 말고, 지금 파이프라인 위에 쌓는 편이 안전하다.

### 1단계. 실패를 분류하고, 담당자 골든셋 20~50개

정확도가 낮다는 느낌만으로는 어디를 고칠지 모른다. 담당자 질문 20~50개를 받아 답을 세 가지로만 나눈다.

- 문서를 못 찾음 (retrieval)
- 문서는 맞는데 표/숫자가 틀림 (parse/table)
- 근거는 있는데 모델이 지어냄 (generation)

이 비율이 나와야 다음 투자가 결정된다. 임베딩을 바꾸는 것보다 이 작업이 먼저다.

### 2단계. 하이브리드 검색 + 메타데이터 + rerank

Milvus dense만 쓰지 말고:

- **키워드/BM25** (품번, 클레임번호, 정확한 한글 용어)
- **메타데이터 필터** (제품, 연도, 문서 종류)
- **reranker** (cross-encoder로 top 50 → top 5)

이 세 가지가 기업 RAG에서 가장 싸게 체감 정확도를 올린다. 특히 시장품질은 고유명사·코드 조회가 많아서 효과가 크다.

Docling을 이미 쓰고 있다면, 변환 결과를 마크다운으로만 버리지 말고 **HybridChunker**로 제목 경로를 붙인다 (`chunker.contextualize`, `repeat_table_header=True`). 표 의존 질문에서 이 차이만으로도 크게 갈린다.

Anthropic **contextual retrieval**(청크마다 LLM이 50–100토큰 맥락을 붙임, 실패율 약 49%↓, rerank까지 하면 67%↓)은 여전히 유효하다. 다만 3,100×100MB에 문서 전체를 청크마다 넣으면 비용이 크다. **1차는 HybridChunker breadcrumb**(문서명·섹션 경로)로 두고, 섹션이 애매한 품질 월보만 LLM 컨텍스트 생성을 켠다.

### 3단계. 엑셀을 벡터에서 분리

xlsx를 Docling → 텍스트 청크로 넣는 순간, “건수/불량률/교차집계” 질문은 구조적으로 실패한다.

- 시트별 컬럼 스키마를 추출
- DuckDB나 SQLite에 적재
- MCP에 `query_tables` 제공
- 벡터에는 **시트 요약 + 컬럼 설명**만 넣어서 “어떤 표를 쿼리할지”만 찾게 함

100MB 파일의 상당수가 엑셀이라면, 이것만으로도 체감이 달라진다.

### 4단계. 문서를 통째로 넣지 말고 계층으로 넣기

100MB PDF를 한 방에 임베딩하지 말고 3층으로 나눈다.

- 문서 요약 (언제, 무슨 제품, 무슨 이슈)
- 섹션/페이지 요약
- 본문 청크 (parent-child: 검색은 작은 청크, 답변 시 부모 섹션을 넣음)

MCP도 맞춰서:

1. `list_documents`로 후보 문서 좁히기
2. `get_outline`으로 목차 보기
3. `get_section`으로 해당 장만 읽기

Codex 같은 에이전트는 이런 multi-step이 가능하니, 벡터 top-5에 모든 답을 맡기지 않는 것이 맞다.

### 5단계. 포맷별 파서 (Docling 단일 경로 폐기)

| 포맷 | 권장 |
|---|---|
| PDF (디지털) | Docling JSON, 마크다운 dump 금지. 표는 별도 객체. 차트는 `--enrich-chart-extraction` |
| PDF (스캔) | RapidOCR `korean` 분기. 텍스트 RAG만 믿으면 안 됨 |
| DOCX | SimplePipeline JSON + HybridChunker. 제목 스타일 보존 |
| DOC | LibreOffice → DOCX. timeout + 파일별 UserInstallation (#3819) |
| XLSX / XLS | calamine/polars → Parquet → SQL. RAG 금지. openpyxl은 폴백 |
| MD | 헤더 기준 분할이면 충분 |
| 차트/그림 | 막대/원/선은 Docling 차트 표. 그 외 VLM. 페이지 검색은 ColQwen |

100MB는 파일 단위가 아니라 **페이지/시트 단위 스트리밍**으로 처리해야 타임아웃과 잘림이 줄어든다.

### 6단계. 차트·스캔이 많으면 페이지 비전 검색을 보조 인덱스로

품질 보고서의 핵심이 Pareto, 트렌드 그래프, 스캔된 클레임 용지라면 텍스트 파이프라인의 천장에 거의 도달한 것이다.

- 페이지를 이미지로 렌더
- **ColQwen2/2.5**를 기본 비전 retriever로 (다국어·작은 글씨에서 ColPali보다 앞섬). ColPali는 더 싼 대안
- 찾은 페이지를 비전 모델로 읽거나, 해당 페이지 텍스트·차트 표와 결합

저장/GPU 비용이 있으니 **차트 많은 PDF에만** 적용하는 것이 현실적이다. 텍스트 + 비전을 같이 쓰면 서로 못 찾는 문서를 보완한다.

## Codex MCP에서 꼭 바꿀 점

검색 품질을 올려도, 도구가 빈약하면 담당자에게는 똑같이 틀린 답으로 보인다.

- `search` 하나만 두지 말 것
- 모든 응답에 **파일명, 페이지/시트, 짧은 인용**을 강제
- 도구 출력을 짧게. Codex 컨텍스트를 청크 덤프로 채우지 말 것
- “모르겠다 / 근거 없음”을 허용. 시장품질은 틀린 인사이트가 맞는 문장보다 위험함
- 제품/기간 필터를 도구 인자로 명시. 모델이 자연어에서 추출하게 두지 말 것

담당자 UX는 채팅 답변보다 **근거 문서로 점프**가 더 중요하다.

## 바로 하지 않는 것이 나은 것

- 임베딩 모델만 교체해서 해결하려는 것
- 3,100개 전체에 GraphRAG를 먼저 까는 것
- 모든 PDF를 비전 RAG로 재인덱싱하는 것
- 청크 크기만 튜닝하는 것

고유명사 사전(품번 동의어, 차종 코드)과 하이브리드 검색이, 임베딩 교체보다 먼저다.

## 권장 실행 순서

실무적으로는 **2단계(하이브리드+메타+rerank)와 3단계(엑셀 분리)** 를 먼저 한다. 파서/비전 교체는 그 다음에 효과가 보인다.

## 후속 확인이 필요한 병목

설계를 더 구체화하려면 아래 세 가지를 먼저 확인한다.

1. 지금 틀린 답이 **문서를 못 찾는 쪽**인지, **숫자는 찾는데 표가 깨지는 쪽**인지
2. 3,100건 중 **xlsx / 스캔 PDF / 차트 많은 보고서** 비중
3. 담당자 질문이 **트렌드 집계**인지, **특정 이슈 원인 추적**인지
